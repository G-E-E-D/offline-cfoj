# Build Offline CFOJ

Build a local Codeforces practice judge for a competitive programmer using a Windows PC. Deliver a working web application in this repository. The user should be able to enter a Codeforces contest ID while online, prepare the entire round, disconnect, restart the application, take the round virtually in Simplified Chinese, submit GNU C++23 solutions, and read the editorials afterwards. The same library must support everyday practice in English or Chinese.

Use Codeforces as the reference for the contestant's workflow. Keep submissions, judging, standings, drafts, and practice history on the user's machine. Choose a maintainable stack and a single documented local judge backend. One-time installation and contest preparation can use the internet. Opening a prepared contest after a cold start must work using only localhost, even with an empty browser cache and both AI providers signed out.

## Import a round by contest ID

1. Make the numeric ID from a public, finished contest URL the only required input. Discover all problems in contest order, including indices such as `A1` and `A2`. Read metadata from the documented API where available and fetch the actual English statements from the public contest pages. Capture the title, duration, scoring information, limits, available tags and ratings, and source URLs. [Codeforces API methods](https://codeforces.com/apiHelp/methods)
2. Preserve the full statement, including input and output specifications, constraints, notes, formulas, tables, diagrams, and every sample pair. Preserve sample line breaks and significant whitespace. Download required assets, rewrite their paths, sanitize imported markup, and render math locally. Preserve the original English text for comparison and retranslation.
3. Show progress per problem for fetching, translation, test preparation, and editorial preparation. Cache successful work. Respect server rate limits and retry transient errors with backoff. Identify the affected problem and offer a retry when a page, asset, or provider is unavailable. A repeated or interrupted import must preserve existing submissions, active virtual rounds, and the last usable contest package.
4. Show which problems can be read, practiced on samples, or fully judged locally. Give the reason and a repair action for incomplete items. A prepared round should expose its contents, data location, and offline readiness from the contest page.

## Prepare both languages and the contest editorial

- Implement two selectable providers, **OpenAI Codex** and **Google Antigravity**. Either provider must be sufficient for translation, test preparation, and editorial generation. Connect to their documented non-interactive interfaces, such as `codex exec` and `agy -p`. Detect the configured executable, report authentication or version issues, and validate structured results before saving them. Pass only the problem materials needed for the job. Keep provider credentials with the provider. [Codex non-interactive mode](https://developers.openai.com/codex/noninteractive) and [Antigravity headless mode](https://antigravity.google/docs/cli/headless/)
- Translate all statement prose and section headings into Simplified Chinese. Preserve math, bounds, variable names, code, literal output tokens, sample data, and references to figures. Check protected fragments against the original before publishing a translation. Let the user regenerate a single failed item.
- Discover the published contest tutorial through the contest materials or linked round posts. Map each explanation to its problem, including tutorials shared by multiple divisions. Retain attribution, original links, formulas, code blocks, and local copies of referenced illustrations. For a problem with no accessible published explanation, generate a clearly attributed AI editorial with an algorithm, correctness argument, and time and space complexity. Check its approach against the problem limits and test any accompanying solution against the validated suite. Surface a failed or unverified section for repair.
- Save **two ordinary UTF-8 Markdown files for the whole round**, for example `data/contests/<id>/editorial.en.md` and `data/contests/<id>/editorial.zh-CN.md`. Each file must have a contents list and an indexed section for every problem. Use relative paths for assets. The web reader must open the matching section of the same local content that the user can read in a Markdown editor.

## Build test data that can support a verdict

- Build the local suite from the statement and public samples even when the original system tests are unavailable. Use AI to design a problem-specific test plan, deterministic input generator, validator, and reference solution or semantic checker. Save the generator, seeds, checker rules, package revision, and validation results so a failing case can be reproduced offline.
- Make the standard target configurable, initially **50 distinct generated cases per ordinary batch problem**, with exhaustive coverage for smaller finite domains. Cover minimum and maximum inputs, boundaries, ties, special structures, plausible wrong approaches, and large inputs that exercise complexity. Validate every input against per-case and aggregate constraints, including sums across multiple test cases. Deduplicate inputs and show which categories were covered.
- Compute required answer files or optimum values by executing a reference solution. Check it against published samples and independently cross-check small cases with a brute-force oracle, enumeration, or a second independently derived solver. Run representative incorrect solutions against the suite. Publish judge data only after validation passes. An oracle disagreement should identify the input, keep the candidate package out of use, and allow repair.
- Select a checker from the problem's output contract. Support token or exact comparison when appropriate, documented numeric tolerances, and semantic checkers for constructive or multiple-answer tasks. Test a semantic checker with distinct valid answers and an invalid one. Interactive, output-only, and special-scoring tasks need their respective local judging components. Keep the statement available and identify the missing component whenever a task cannot yet be judged. Label sample-only runs and locally generated suites accurately in the UI.

## Judge C++23 on the user's machine

- Provide a source editor with saved per-problem drafts, paste and `.cpp` upload, sample runs, custom input, and submission against the full local suite. Queue submissions, show live progress, compile once per submission with a real GNU C++23 toolchain (for example `g++ -std=gnu++23 -O2 -pipe`), and run cases under the problem's time and memory limits.
- Use an isolated, network-disabled runner for compilation and execution, including generated tools. Give contestant programs only their permitted input and scratch space. Enforce time, memory, process, and output limits and clean up the process tree. Choose a Windows-compatible isolation path, such as a locally cached Linux container under WSL2. Check compiler and runner availability during setup and provide an actionable error if either is unavailable.
- Show queued, compiling, running, and final states. Distinguish Accepted, Wrong Answer, Compilation Error, Runtime Error, Time Limit Exceeded, Memory Limit Exceeded, Output Limit Exceeded, and judge failures. Save the submitted source, timestamp, mode, toolchain, test package revision, verdict, measured runtime and peak memory, compiler diagnostics, and first failing test where applicable. Recover interrupted jobs under their original submission IDs. Keep sample and custom runs out of scored submission history.

## Practice, virtual participation, and the web interface

- **Daily practice.** Provide a searchable contest library and problemset with filters for contest, index, rating, tags, and solve status. A problem page should put the statement, examples, editor, submission history, and its editorial within reach. Persist attempts and solved status across restarts.
- **Virtual participation (VP).** Offer start now or a scheduled local start for the original contest duration. Persist the start, deadline, scoring rules, and package revision. Derive time from the local backend so a refresh or restart resumes the same clock. Show contest problems, submissions, countdown, and local standings. Apply the round's documented VP rules, including solve time and eligible failed attempts under ICPC rules or time-adjusted points where applicable. Display scoring, tie-breaks, and any local fallback. If historical standings were imported, make them available for offline comparison after the round. [Codeforces contest workflow](https://codeforces.com/contest/4)
- **Contest integrity.** Keep future problems hidden until the start. During VP, hide editorials, tags, private tests, and solution-revealing diagnostics for that round across normal navigation. Classify a submission by when the backend received it, even if judging finishes after the deadline. At expiry, unlock editorials and route new submissions to practice. Finalize the VP scoreboard after all eligible submissions have been judged.
- **Bilingual UI.** Put a one-click English / Simplified Chinese switch on every main screen. It must switch navigation, controls, statuses, verdict descriptions, and the current statement or editorial together, entirely from disk. Preserve the route, draft, scroll location, and active VP session. Remember the language across restarts. If a translation is missing, identify the displayed language and offer regeneration during online preparation.
- **Usability.** Give the web UI a modern, responsive layout with clear type hierarchy and visible keyboard focus. Make importing a round, continuing practice, and resuming a VP easy to find. Give the statement room for formulas and long samples, with copy buttons beside samples and the editor alongside it on wide screens. Support narrower windows, readable Chinese typography, and verdict text that works without color. Bundle frontend assets, fonts, editor, and math renderer locally.

## Acceptance run

1. Import public contest **4** by entering only its ID. Verify that A through D appear in order, both languages are available, assets load locally, and each editorial file opens directly on disk with four problem sections. Exercise a provider through its real adapter when credentials are available. Test both adapters' success and failure paths with repeatable fixtures. Report which live integrations were exercised.
2. For **4A, Watermelon**, the published sample `8` yields `YES`. A submission that prints `YES` for even weights and `NO` for odd weights must pass the sample and receive Wrong Answer on weight `2`. A correct C++23 solution must receive Accepted. For **4B**, use input lines `2 3`, `1 2`, and `1 2`. After `YES`, the checker must accept either schedule `1 2` or `2 1` and reject `2 2`. [4A statement](https://codeforces.com/contest/4/problem/A) and [4B statement](https://codeforces.com/contest/4/problem/B)
3. Block external network access while keeping loopback available. Restart the app and judge, open a fresh browser profile, switch languages while editing, run a sample, submit correct and incorrect programs, view their results, and open the local Markdown editorial. Verify that the browser, backend, and runner require no external requests. Exercise compiler and resource-limit verdicts against a small deterministic fixture.
4. Start a short VP using a test clock or fixture, submit just before expiry, refresh and restart, then finish judging after expiry. Verify the original deadline, spoiler handling, correct score, and post-contest editorial access. Submit an upsolve and confirm the recorded VP result stays intact.
5. Interrupt an import, resume it, and reimport the same contest. Verify deduplication and that drafts, submissions, and an earlier VP are still readable. Keep an offline fixture that exercises the same import and judge paths when a live site or provider is unavailable.

Run these checks through the application's normal entry points. Deliver the implementation, the startup command, a short account of the checks actually run, and any remaining limits that affect which contests can be judged locally.
